# Meownero native UI decision, 2026-10-10

Recommend **Qt Quick/QML 6.12.0 with a shared C++ application controller**, driving the existing pinned C++ wallet through a narrow authenticated local RPC client. Runner-up is **Slint 1.18.1 with its released C++ API**. This selects the implementation direction; independent design acceptance and real wallet integration remain pending.

Qt fits the current C++ code, has the strongest desktop control/accessibility history of these candidates, and has the upstream Monero GUI precedent. That precedent does not prove compatibility with our FCMP++/CARROT pin or audit this wallet. QML renders its own controls in a native application. It is neither a WebView nor a guarantee of actual OS-native widgets. Use standard Qt Quick Controls with custom styling before inventing safety-critical controls. [Qt accessibility](https://doc.qt.io/qt-6/accessible-qtquick.html), [Monero GUI](https://github.com/monero-project/monero-gui/blob/master/README.md), [Qt 6.12 release](https://www.qt.io/blog/qt-6.12-released).

The repository was inspected at `0f60722fb0eeb349a524cf73416d736edf49d9cd`. The accepted backend remains the local Vanguard kit. Its upstream is `seraphis-migration/monero@e151643c5269c83bf24a83b2548e2493876026b2`, pinned in `vanguard/source-lock.json`; its FCMP Rust FFI is already part of that core. Do not replace wallet construction, signing or cryptography to fit a toolkit. Current accepted execution is build-mac ARM64 in a container on valueless accelerated regtest. Desktop OS support, signing and downloads remain targets.

All seven allow Windows/macOS/Linux UI code reuse in their supported configurations. This does not establish our C++ backend portability. Qt, Flutter and the Go candidates advertise mobile paths; mobile is comparison evidence only. Slint's [released 1.18.1 guide](https://github.com/slint-ui/slint/blob/v1.18.1/docs/astro/src/content/docs/guide/platforms/mobile/general.mdx) supports Rust/C++ on Android but Rust only on iOS. Do not substitute master-only C++ iOS work. Iced and egui are not accepted mobile paths for this project.

[Tauri](https://v2.tauri.app/reference/webview-versions/) and [Wails](https://wails.io/docs/introduction/) use system WebViews. Their native host executables avoid bundled Electron, but their HTML UI remains WebView-based and inherits platform WebView/bridge/security differences. They fail the preferred native-rendering direction here.

Thin AppKit/SwiftUI, WinUI and GTK views around a shared C++ core could offer stronger system conventions and accessibility on their own OS. They require three maintained view implementations and platform bindings. No measured evidence here shows that benefit outweighs Qt for the current desktop scope. Keep native dialogs/menu integration and switch a problematic flow to a thin native view if actual journey evidence warrants it; do not promise one-codebase OS-native widgets.

## Shared boundary and safety

The chosen boundary is UI → typed C++ controller → authenticated loopback wallet RPC → unchanged wallet core. Preserve existing Docker-first backend ownership and isolation. The controller owns exact atomic integers, session identity, async request cancellation, bounded responses and an allowlist of methods. QML sees display models and explicit actions, not arbitrary RPC or credentials. Do not expose arbitrary endpoints, URLs, file reads or shell commands through UI bindings. Bundled trusted QML only; no remote QML, WebEngine or web renderer. UI-thread work stays small; wallet scans and transaction construction run asynchronously.

Direct C++ wallet-library integration is simpler at the language boundary, but compiling and packaging that library against the exact Vanguard pin is not yet evidenced. It would change the isolation/lifetime boundary and requires a separate reviewed implementation check. Prefer the existing demonstrated process/RPC interface first. Rust alternatives add repr(C)/allocation/free/exception contracts; Go adds cgo/pointer lifetime; Dart adds C ABI/native allocation. None is a reason to rewrite the core.

Reuse [TJS-1994 privacy constraints](/TJS/issues/TJS-1994#document-privacy-constraints), exact revision `4a98299b-dfa7-4ac8-82f9-c959af5f43eb`, without a duplicate privacy review. In particular:

- Loopback is not authentication. Use fresh private wallet RPC Digest credentials and daemon administrative auth. The kit's disabled login is not a desktop default; its private AF_UNIX bridge carries P2P, not wallet administrative RPC.
- Keep seed copy/export disabled in the prototype. Re-reveal requires wallet-password authentication, no prefetch while locked, no seed in persistent QML state, logs, crash exports or captures. Hide on navigation/background/lock. Owned buffer wiping cannot erase all framework/core copies or external clipboard history.
- Bind amount, recipient, fee and total to one prepared transaction and session. Wallet `relay_tx {hex}` takes private pending metadata; it is not the daemon's `relay_tx {txids}`. The proposed wallet fee-review/relay flow remains unverified. Do not silently reconstruct after approval. Preserve an unknown submission state and reconcile before another payment.
- Current addresses use upstream Monero `4…` encoding. Actual receive text comes from RPC; mock fixtures are invalid and explicitly simulated. Keep the local-regtest warning and known-session recipient limits; never ask users to import a personal seed or deposit real XMR. Distinguish total from unlocked funds and sync from a completed empty wallet.

Framework maturity, published security process, reviewed crypto components and an audited end-to-end wallet are different claims. `vanguard/source-lock.json` records partial upstream audit coverage and unresolved scope limits. [Qt's shared security model](https://doc.qt.io/qt-6.12/shared-security-model.html) likewise leaves application behavior to us. None of the prototype, this decision or the chosen toolkit closes the project's production assurance gates.

## Licensing and release ownership

Qt is available under LGPLv3/GPL/commercial routes, with module-specific exceptions. Start with eligible open-source Qt modules, dynamic deployment, license notices, corresponding Qt source/modification access and user replacement/relinking requirements. Static distribution needs a deliberate relinking/installation-information package; do not assume static linking removes LGPL obligations. GPL-only modules change the application distribution obligations. No paid license was authorized. [Qt obligations](https://www.qt.io/development/open-source-lgpl-obligations). The LTS label does not grant free access to every commercial maintenance patch; stay on publicly available security-fixed releases and record the chosen license/module manifest.

Slint 1.18.1 offers GPLv3, royalty-free 2.0 or commercial licensing. The free desktop/mobile royalty-free route requires visible Slint disclosure, such as AboutSlint; embedded use is excluded. The alternative GPL route has its own distribution terms. Do not describe Slint as MIT; examples/docs differ from its runtime. [Pinned license](https://github.com/slint-ui/slint/blob/v1.18.1/LICENSE.md). Flutter BSD-3-Clause, Iced/egui MIT or Apache-2.0, Fyne BSD-3-Clause and Gio MIT are permissive baselines, but dependencies/fonts/assets still need a complete inventory.

All candidates require application-owned signing/updating. For Qt use its deployment tools and standard OS packaging; Slint ships native SDK artifacts; Flutter ships an engine/assets bundle; Fyne/Gio packaging tools do not create trust by themselves. Freeze dependency locks, source/toolchain and artifact hashes, SBOM/license inventory and security-advisory coverage. Verify signatures and the signed update manifest/payload before replacement, preserve wallet data and rollback, refuse downgrade or wrong-architecture packages, and never trust a website filename alone. Code signing/notarization on macOS and Windows, Linux package integrity and actual download verification are later evidence gates. No release, matrix run, upload for public distribution or updater was started.

The measurements are **not a fair toolkit ranking**. Qt includes Python/shiboken and a different renderer; Slint uses software rendering. SDK/environment sizes are not shipping installer sizes. Zero observed ticks over four seconds means below this probe's time resolution, not guaranteed zero CPU. Cache and shared desktop load were uncontrolled; these are single local observations, not startup statistics. No comparable startup/idle/footprint measurements were taken for Flutter, Iced, egui, Fyne or Gio.

Failures are retained. Qt first aborted because libxcb-cursor.so.0 was absent; Ubuntu package 0.1.4-1build1 was extracted into scratch only. The next Qt capture failed because QtQuick Python bindings were not registered; importing QQuickWindow fixed that fixture. The first Slint XSendEvent keyboard injection did not change state; selecting and verifying the actual active owned window, then using XTest input, produced the recorded journey. Final Qt emitted a GetApplicationBusAddress warning, and Slint's AT-SPI client emitted an AddAccessible signature warning. Both completed the assistive API actions despite those warnings.

**Unconfirmed**: an audible Orca journey was not run; AT-SPI actions are narrower evidence than a screen-reader user completing the task. NVDA/VoiceOver, IME, high-DPI, reduced-motion behavior, real create/import, secure seed reveal/quiz, wallet fee-review relay, full C++ Qt packaging, macOS/Windows, signing and update verification remain untested. Screen-reader QA needs an owned usable reader session and actual journey evidence before acceptance. Backup/restore navigation was mocked; it did not restore a wallet.

Evidence consists of the source fixtures, raw/final and failed-probe results, exact source hashes, captured owned windows and run/cleanup records in the uploaded native experiment bundle.
