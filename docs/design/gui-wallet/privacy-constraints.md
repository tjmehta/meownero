**Numbered constraints**

1. **MUST** label every screen, receive address/QR and send review as local accelerated regtest, with valueless coins; keep simulated interactions visibly labeled. **MUST NOT** offer live mainnet/public-testnet switching or imply a cross-platform native release is supported. Current backend support is only build-mac ARM64 in a container; selected 9 MEOW/90-second policy is not integrated. Evidence: K; `research/current-evidence.md`.

2. **MUST** display the exact RPC-returned primary address: currently `4…`, inherited Monero prefix 18. **MUST NOT** substitute `M…`/`T…`, add a cosmetic prefix, or claim checksum/nettype validation distinguishes this regtest from Monero mainnet. The provisional identity spec belongs to the older patched lineage. For a future live kit GUI, bind RPC, data directories and recipient selection to the owned isolated session; only enable sends to session-known disposable recipients until a network-isolation/address workflow is validated. Never direct users to deposit real XMR or import a personal seed; do not offer interoperable `monero:` payment links. A raw address/QR remains ambiguous outside the GUI. Evidence: U:`src/cryptonote_config.h:261–263`; P:`daemon` uses `--regtest`; `docs/spec/network-identity.md`; public soak `research/evidence/vanguard-daemon-soak-tjs1816-2026-10-08/receipts/run1/public/result.json` (`addresses`). Session-recipient enforcement is **[UNVERIFIED]** GUI work; inspected K/R/P.

3. **MUST** derive spendable funds from refreshed wallet RPC. Current constants are coinbase **60 blocks**, normal received outputs **10 blocks**; explicit locks and reorgs can extend this. In height terms, a default received output at block index b unlocks when wallet chain height reaches b+10; coinbase uses `unlock_time=b+60`. **MUST NOT** turn these into guaranteed minutes or a countdown independent of chain progress. Evidence: U:`src/cryptonote_config.h:43,48`; `src/cryptonote_core/cryptonote_tx_utils.cpp:224`; `src/cryptonote_basic/cryptonote_format_utils.cpp:2095–2116`; `src/wallet/wallet2.cpp:7651–7676`. Kit mines 70 funding blocks and 12 confirmation blocks (R).

4. **MUST** keep wallet/daemon RPC on explicit IPv4 loopback; use IPv6 loopback only if explicitly enabled. Keep the kit's network-disabled container and owned private files. A real desktop integration MUST enable wallet RPC Digest auth (fresh private credentials) and daemon RPC auth for administrative access; wallet-file encryption is a separate control. **MUST NOT** copy `--disable-rpc-login` into an ordinary desktop launch, publish container RPC ports, allow arbitrary origins, or expose credentials to untrusted renderer content. Loopback alone does not authenticate local callers. Evidence: R:32–36; P:`daemon`,`live_listeners`; U:`src/wallet/wallet_rpc_server.cpp:340–445`; `src/rpc/rpc_args.cpp`; `research/resume-privacy-2026-09-12.md`. Authenticated current-GUI integration is **[UNVERIFIED]**, inspected K/R/P and U initialization.

5. **MUST NOT** advertise native Unix-socket RPC as proven. The kit's mode-0600 AF_UNIX socket bridges **P2P Levin traffic**, while wallet/daemon RPC uses loopback HTTP TCP. Keep those boundaries distinct. Direct AF_UNIX administrative RPC integration is **[UNVERIFIED]**; inspected P:`Bridge`, R:`start_wallet`, U RPC initialization. Any future socket boundary requires its own integration check and user-only directory/socket permissions.

6. **MUST** explicitly use `--trusted-daemon` only for the owned node the user runs and controls. For anyone else's node, including a remote node behind a local proxy/tunnel, use explicit `--untrusted-daemon` (or `set_daemon trusted:false`). **MUST NOT** infer trust from “localhost”: upstream auto-trusts local endpoints when no trust flag is supplied. “Trusted” enables privileged assumptions; it is not a privacy guarantee. Evidence: U:`src/wallet/wallet2.cpp:458–480`; R:34; `research/wallet-transport-2026-09-18.md` runtime trust correction. Current Vanguard untrusted-mode execution remains **[UNVERIFIED]**, inspected R/P and K.

7. **MUST** require successful wallet-password authentication before revealing an existing seed again; an app-unlock animation or OS appearance setting is insufficient. Do not query/prefetch the seed while locked. **MUST NOT** say the RPC already enforces this: `query_key` takes only `key_type`; it retrieves the opened wallet's seed without verifying its password. Evidence: U:`src/wallet/wallet_rpc_server_commands_defs.h::COMMAND_RPC_QUERY_KEY`; `wallet_rpc_server.cpp:2333–2385`. Password-gated reveal is **[UNVERIFIED]** GUI work; current kit uses empty passwords.

8. **MUST** leave seed copy/export disabled in this prototype; use explicit reveal and a backup quiz without persisting quiz answers. If a later reviewed implementation enables copy, it MUST require an explicit action after authentication, warn about clipboard history/sync, and attempt clearing after **30 seconds** or on hiding/locking, only if the clipboard still contains the copied seed. **MUST NOT** promise auto-clear erases clipboard managers, synced copies or another process's capture. This is a proposed GUI rule, **[UNVERIFIED]**; inspected K/R/P, which contain no clipboard implementation.

9. **MUST** hide the revealed seed on leaving the screen, app/background or session lock; exclude it from app thumbnails, screenshots/recordings made by the app and all design/test evidence. Warn users to stop recording before reveal; use platform capture protection where available. **MUST NOT** promise protection from arbitrary OS capture, cameras or malware. Capture prevention is **[UNVERIFIED]**; inspected K/R/P, no native OS implementation.

10. **MUST** exclude seed/password/key and restore request/response bodies, tx secret keys and private pending-tx metadata from logs, analytics, crash-report attachments and support exports. Allowlist diagnostic fields; do not merely redact a few names. Limit seed lifetime to the reveal/restore operation, avoid persistent UI state and unnecessary copies, and wipe owned mutable buffers when possible. **MUST NOT** claim complete memory zeroization: upstream copies its wipeable seed into `std::string` for the RPC response; deleting a reference is not proof of erasure. Evidence: K export restrictions; `vanguard/tester-native.py`, `vanguard/tester-public-schema.json`; U:`wallet_rpc_server.cpp:2345,2385`; R:140. Native UI memory/crash-report controls are **[UNVERIFIED]**.

11. **MUST** explain observer boundaries. The local controller can see addresses, amounts and seed RPC; an untrusted daemon sees client connection metadata, request sizes/timing/scan patterns and the transaction submitted to it, allowing first-submission linkage. Untrusted mode restricts assumptions; it does not hide that metadata or make node responses honest. **MUST NOT** port RingCT decoy-request counts or intersection results into FCMP++ claims. Tested older transport: loopback source, request sequence and one transparent 503 sync retry. **[UNVERIFIED]** current/public exposure, real public IP, repeated correlation and traffic-analysis resistance: inspected `research/wallet-transport-2026-09-18.md` and K. Public direct-node IP exposure is an architectural inference, not a current-kit measurement.

12. **MUST** keep Tor/I2P and DNS/OpenAlias choices disabled or visibly simulated pending current-lineage tests. Older controller evidence proves loopback SOCKS4a/TLS routing/refusal and **52/52 cases**, not a Tor/I2P network. It also observed OpenAlias DNS despite `--no-dns`; current U calls `is_dns_enabled()` in transfer and validation paths, so do not claim that older leak was reproduced here. Enforce literal addresses and `validate_address {any_net_type:false,allow_openalias:false}` in a future validated send flow, checking every address-taking RPC; neither `--restricted-rpc` nor a proxy alone is a complete egress boundary. Remote-node TLS authenticates the endpoint, not its chain data; any supported proxied route must fail closed without direct fallback. Evidence: `research/resume-privacy-2026-09-12.md`; `chain/privacy-test.py:470–516`; U:`wallet_rpc_server.cpp:1075,4788`. Actual Tor/I2P, current DNS isolation and proxy integration are **[UNVERIFIED]**, inspected these sources and K. Preserve the completed 52-case checkpoint.

13. **MUST** explain that a seed rescan recovers on-chain funds/spend capability, not local notes, labels, address book, app settings or the previous wallet password. Advise a separate protected wallet/app backup for local data. **MUST NOT** say all history/metadata is restored or all outgoing information is lost: some spend/fee history was recovered in the older lineage, while equivalent full Vanguard-history recovery is unverified. Use a height before the first relevant payment (0 when unknown); don't present scan-in-progress as an empty finished wallet. Warn and preserve local metadata before a destructive hard rescan. Evidence: K; R:128–155; U:`src/wallet/wallet2.h` serialized `m_tx_notes/m_address_book/m_subaddress_labels`; `wallet2.cpp:4844–4848,7621–7639`; `research/swarm-demo-2026-09-12.md` tested note loss; `research/wallet-funded-2026-09-18.md` tested outgoing txid/fee recovery. Notes/labels/address-book recovery was not tested in this kit.

14. **MUST** distinguish “Prepared”, “Submitting”, “Submission status unknown”, “In pool”, “Confirmed” and “Unlocked”; allow rollback after a reorg. On a connection drop/timeout during send, retain the attempt's available identity privately and reconcile wallet/daemon state before permitting another payment; do not blindly create a replacement transfer. **MUST NOT** report success, definite failure, restored/fully synced status, or irreversible finality without the corresponding evidence. A 503 sync retry does not prove send retry safety. Evidence: R:198–224,261–284; U:`src/wallet/wallet2.cpp:7892–7942` submits before updating local unconfirmed state. Mid-submit drop/reconciliation UI is **[UNVERIFIED]**; inspected `research/wallet-transport-2026-09-18.md`, R and U.

15. **MUST** show fee/total as integer atomic-unit values converted without rounding nonzero payments away (current scale 10^12); derive the eventual fee review from the exact prepared transaction. **MUST NOT** silently rebuild/relay a different transaction after approval, advertise fixed/zero fees, a real MEOW exchange price, “anonymous”, “untraceable”, “100% private”, “guaranteed unlinkable”, “production-ready” or “externally audited”. No ring-16 explanation for current FCMP++ transfers. Evidence: R:17,51–55; `vanguard/daemon-soak.py` fee accounting and `verify-daemon-soak.py:412–413`; `vanguard/source-lock.json` assurance caveats; K. Fee-review UI is **[UNVERIFIED]**.

**Approved short wording**

- Persistent network label: **“Local regtest · Test coins only”**
- Network detail: **“An isolated, accelerated FCMP++/CARROT test chain. Coins have no value.”**
- Receive warning: **“Test address only. It uses Monero's address format. Do not send real Monero here.”**
- Current privacy explanation: **“This local test uses FCMP++ and CARROT for transaction privacy. It does not establish anonymity or Internet privacy.”**
- Future remote-node explanation: **“An untrusted node can observe your connection and request activity and link submitted transactions to that connection. Untrusted mode does not hide this metadata.”**
- Restore explanation: **“Your seed recovers on-chain funds and spending access after scanning. It does not recover local notes, labels or contacts.”**
- Unknown submission: **“Submission status unknown. Check this payment before trying again.”**
- Prototype banner: **“Interactive prototype · Wallet actions are simulated”** wherever actions are simulated.

**Observed behavior:** the short kit covers two-destination transfers and offline construction, but not generic `get_info`; its AF_UNIX bridge is P2P, and full password/fee-review/remote-node GUI flows remain unverified. Design lead owns applying these constraints on TJS-1992. This advisory deliverable is complete; no source needed for the requested assessment is missing. **Needs TJ: None.**
