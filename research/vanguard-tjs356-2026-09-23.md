# TJS-356: Vanguard V1, pinned FCMP++ and CARROT primitives in an isolated harness

2026-09-23. Privacy Cryptography role. The harness compiles the actual upstream FCMP++ and
CARROT code at a pinned commit, then runs 187 positive and negative vectors against it. It
runs twice, in a network-less container. It is valueless: no node, no network, no keys of
value, no spending. The accepted testnet v0 recipes and their builder image are untouched.

**This is agent review, not an external audit.** Nothing here supports an audit, security or
mainnet-readiness claim for Meownero, FCMP++ or CARROT.

Commits (not pushed):
- `3df2538` pins
- `79f8344` harness, verifier and tamper controls
- the commit that adds this document also adds `research/evidence/vanguard-tjs356-2026-09-23/`

Result: 187 of 187 vectors match their expectation or reproduce exactly one of two documented
findings, VG-F1 (7 vectors) and VG-F2 (4 vectors). results.json is byte-identical across the
two runs. `vanguard/verify.py` prints `PASS_VANGUARD_RECEIPTS vectors=187 known_findings=11
upstream=e151643c5269 addresses_decoded=12`. `vanguard/test-verify-refusals.py` prints
`PASS_VANGUARD_REFUSALS`: nine tampered copies of the evidence are refused.

## Findings

These are API-level observations at the pin. Both are guarded on the consensus path I traced.
I did not prove that every caller of the verify APIs runs behind those guards.

### VG-F1: FCMP++ verification accepts trailing bytes (7 vectors, deterministic)

Observed: `fcmp_pp::verify` and `fcmp_pp::verify_membership` accept a valid proof with one
appended byte. This holds for all five upstream vectors and both fresh proofs.

Cause, at the pin:
- `src/fcmp_pp/fcmp_pp_rust/src/lib.rs:1002` checks the length only with `debug_assert_eq!`, which is compiled out here: every non-`Debug` CMake build type builds the Rust crate with `--release` (`src/fcmp_pp/fcmp_pp_rust/CMakeLists.txt:97-108`).
- `FcmpPlusPlus::read` (`:1023`) consumes the expected bytes, and the remainder is never checked.
- `fcmp_pp_verify_membership` (`:1102`) calls monero-oxide `Fcmp::read` (`crypto/fcmps/src/lib.rs:991-997` @ `31c26d9`), which `read_exact`s `proof_size` bytes and likewise ignores the rest.

Guard: `is_canonical_fcmp_plus_plus_layout` requires the exact size
(`src/cryptonote_core/tx_verification_utils.cpp:304-306`) and is called from
`ver_non_input_consensus` (`:826`).

Assessment: **low**, a defense-in-depth API contract gap. Without the layout check, a relayed
or stored proof would be malleable in length while still verifying. The risk is to any caller
that trusts `verify` alone, and to future integrators. In a debug Rust build the same input
would hit the `debug_assert` and abort instead; that build was not exercised.

### VG-F2: an `n_layers` claim of the other root curve aborts the process (4 deterministic vectors; also reached by fresh proofs)

Observed: with `n_layers − 1`, the process dies with SIGABRT after the Rust panic `claimed root
is on a distinct layer than tree root`. The panic is at monero-oxide `crypto/fcmps/src/lib.rs:933`
@ `31c26d9`.
- Upstream 1/4/8/128-input vectors: SIGABRT.
- Upstream 2-input vector: returns false.
- Fresh 1in and 2in proofs: SIGABRT in run 1 and false in run 2 (`run1/metrics.json` `random_input_observed`, `run1/stdout.log`).

The panic is reached only after `read_commitments` (`:888-889`) has decoded the commitments
under the wrong layer count. Whether the misaligned bytes still decode as points depends on
the proof bytes, so honest random proofs hit it some of the time.

Guard: consensus binds the transaction's `n_tree_layers` to the stored root
(`src/cryptonote_core/blockchain.cpp:117` and `tx_verification_utils.cpp:447`). It then
decompresses the root with that same layer count (`:455`), so the claimed layer parity and the
root curve agree on that path.

Assessment: **low** at the pin, as robustness and defense in depth. It would be a remote crash
wherever an untrusted layer count reaches `verify` or `verify_membership` alongside an
independently sourced root: wallets, verification services or future callers. It may overlap
Trail of Bits finding #6 (FFI, "partially resolved"); I have not verified that and do not
claim it.

### Harness consequence

Fresh proofs are random, and VG-F2 is data-dependent. For `fcmp_pp.fresh*` and `sal.*`
vectors, `results.json` therefore records only the verdict class, and each run's
`metrics.json` keeps the raw verdict. The first design recorded raw verdicts, and this run
would have failed its byte-identity check. The findings are only marked on the fixed upstream
vectors, where the bytes are pinned.

## Limits

- Sampled mutations, not soundness or zero-knowledge arguments. No claim is made about the security of FCMP++, the generalized bulletproofs, divisors, helioselene or CARROT.
- **FCMP++ coverage.**
  - Batch verification `fcmp_pp::verify(std::vector<FcmpPpVerifyInput>)` is not exercised.
  - Trees are small: 7 layers for the upstream vectors, 4 for the fresh tree.
- **Transaction-level checks are not exercised:** no transaction construction, no BP+ range proofs, no balance equation.
- **CARROT coverage:**
  - Only the normal external enote path is scanned.
  - Not covered: internal and self-send enotes, Janus protections beyond one input context change, special enotes, view-only or hybrid wallets, and CARROT-to-FCMP++ spend end to end.
- **The build is not bit-reproducible.** The fresh-proof and SA/L verdict classes are reproducible; their bytes are not.
- The stage branch moves. Everything here is about `e151643c` and `31c26d96` only.
