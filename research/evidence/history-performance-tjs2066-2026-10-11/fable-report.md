## What the code does on toggleExact

The path is `toggleExact` → `refreshModels` → two full `ActivityModel::refresh()` calls → `emit changed()`. Each refresh does `beginResetModel` / `endResetModel` and rebuilds every row by calling `WalletController::detail(tx->id)` per row (`activitymodel.cpp:52`). The hot spots, in order of cost:

- **Quadratic lookup.** `detail()` calls `Ledger::find(id)`, a linear scan over `txs` (`ledger.cpp:78`). For N rows that is N²/2 string compares, done twice, since `m_recent` also scans the whole ledger before honoring its limit. At N=1000 that is about one million `QString` compares per toggle.
- **Over-formatting per row.** `detail()` builds a 17-key `QVariantMap` with two `amountView` calls, each of which calls `amount::format` twice (`walletcontroller.cpp:376`). The row needs only one of the eight `Formatted` results plus `full.text()`. `amount::format` copies a `QLocale` and calls `setNumberOptions` on every call.
- **Repeated `QStringLiteral("rowAmount")` map lookups** and `QVariant` boxing per row. Small per row, but it is 9 strings per row through `QVariant`.
- **`sorted()` allocates a new pointer list and stable-sorts on every refresh** (`ledger.cpp:105`), twice per toggle. Cheap relative to the above, but it is the only place the pending-first order is defined, so the optimized path must keep going through it or an equivalent.
- **The model reset is the render bottleneck, not the C++.** `ActivityList.qml` is a `Repeater` inside a `Column`, not a `ListView`. A reset destroys and recreates every delegate. Each delegate is an `AbstractButton` with nested `RowLayout`/`ColumnLayout`, three `AText`, an `AmountLabel` (three `Text` items), and up to two `Icon` items, each of which is a `Shape` with `CurveRenderer` and a `PathSvg` parse. That is roughly 15 items and two shape tessellations per row, times N. At N=1000 this is the multi-second case, and it also re-emits every accessible name.
- **`emit changed()` afterwards fans out to every `Wallet.*` property binding** in the loaded page, including `Wallet.balance` (recomputes `balances()` over all txs, plus three `amountView` calls), `send`, `node`, `condition`, `onb`, and `fixtures`. On Overview this re-evaluates `page.b` and the big `AmountLabel`. For N=4 this is comparable in cost to the model work; for N=1000 it is small.

Separately, the Overview card's `Repeater` is driven by `m_recent`, which is a second independent model rebuilt from scratch, so Overview pays the full N² lookup for 4 rows.

## Minimal optimization plan

Ordered so each step is independently shippable and testable, and so the delegate contract (role names, pending-first order, text, accessible names) does not change.

1. **Replace reset with `dataChanged` when the row set is unchanged.** In `refresh()`, build the new `QList<Row>` first. If the new id sequence equals the old one, swap the row storage and emit one `dataChanged(index(0), index(n-1), {AmountTextRole, MoreDigitsRole, AmountAccessibleRole, StatusTextRole, StatusKindRole, SubtitleRole, TitleRole})`. Otherwise fall back to the existing reset. This is the single change that removes the delegate churn on toggle. Toggle only changes amount text, so `dataChanged` is exactly right there. Confirmation changes (`onBlocks`, `fixtureAddBlocks`) keep the id set but change order (a pending tx gets a height and moves below newer confirmed ones), so the id-sequence equality check correctly falls back to a reset. Do not try to emit `rowsMoved` in this task.
2. **Index the ledger once per refresh instead of `find` per row.** Either give `detail()` a `const Tx &` overload used by the model (the `QString` overload stays for QML), or have `refresh()` compute the row directly from the `Tx*` it already holds from `sorted()`. This removes the N² term without touching `Ledger`.
3. **Compute only the row amount.** Add a narrow helper, for example `rowAmount(const Tx&)`, returning the `{text, more, accessible}` triple with one `amount::format(magnitude, out, m_exact, true)` and one exact format. That cuts formatting work per row by 4x and avoids the 17-key map entirely for list rows. Keep the `detail()` map for the dialog unchanged so `DetailDialog.qml` is untouched.
4. **Honor `m_limit` before the work, not after.** `m_recent` should stop after 4 rows of `sorted()`, which it does, but step 2 must preserve that the 4 rows are the first 4 of the same sorted sequence as `m_activity`, so the Overview card and the Activity page agree.
5. **Optional, only if the frame measurement still shows it:** cache `amount::format`'s grouping `QLocale` in the controller (one `setNumberOptions` per locale change rather than per call), and hoist `sorted()` to run once per `refreshModels()` and feed both models. These are second-order.

Not recommended for this task: switching `Repeater` to `ListView` with reuse, or `QQmlListModel`. Both change focus, tab order, and accessibility-tree membership, and the user-visible contract that every row is in the tree is what the journey QA accepted.

**Pitfalls to preserve while doing the above:**

- **Order and pending-first.** Order is defined only by `Ledger::sorted()`'s comparator (`height.value_or(1e9)` descending, stable). Any change must keep calling it or reproduce it exactly, including stable ordering among same-height rows, which is insertion order and which the fixtures rely on (`s1` pending above `r1`).
- **`countChanged` semantics.** Today it fires only when the row count changes. Keep that, since `ActivityPage.qml` and `OverviewPage.qml` bind `visible` to `count`.
- **`dataChanged` must include every role the delegate reads.** The delegate uses required properties for all nine roles. Omitting `AmountAccessibleRole` would leave `Accessible.name` stale, which is the exact a11y regression the task forbids. Emitting all roles except `RowIdRole` and `IconRole` is correct and simpler than tracking which changed.
- **Focus.** With a reset, the focused row is destroyed and the reason is lost. With `dataChanged` the row survives, so focus stays on it, which is strictly better and matches the Overview N5 rule ("focus stays on the balance"). But check `fallbackFocus` behaviour after `onChecked`: that path changes `status`, not the id set, so it will now take the `dataChanged` branch. `DetailDialog` closes via `reconciled` and `returnTarget()` will now find the opener row still alive and visible, so focus returns to the row instead of the heading. This is the F5 case from commit fdd7b7b. Decide explicitly whether returning to the row is the wanted behaviour; it reads as an improvement, but it changes an accepted journey, so the journey harness assertion for F5 needs updating or the reconcile path must keep forcing a reset.
- **Reconciliation ordering.** `onChecked` does `refreshModels()` → `emit changed()` → `emit reconciled(rowId)`. Keep that order. The dialog's `d` binding depends on `Wallet.balance` and `Wallet.tip`, so `changed()` must still precede `reconciled()` or the dialog may close against stale `d`.
- **Reset still needed on `loadWallet`, `fixtureSetStory`, `onRelayFinished`, `onBlocks`, `fixtureReorg`.** All of those change the id set or order. The id-sequence check handles them automatically; do not special-case.
- **`m_recent` limit plus `dataChanged`.** If the ledger grows but the first 4 ids are unchanged, `m_recent` takes the `dataChanged` branch while `m_activity` resets. That is correct, but the benchmark counters should expect the two models to diverge.
- **Icon role.** `IconRole` depends on `type` only and never changes for a given id, so it can be excluded from `dataChanged`. If a future change allows type to change, include it.

## Benchmark design critique

The design is sound in shape. Specific points:

- **Workload.** 4/100/1000 unique mixed-type records is right, but "mixed" must include at least one row of each of: pending Out, Unknown, Failed, Mined group, In with note, In without note, confirmed Out to kit wallet, confirmed Out to literal address. Otherwise step 3's narrow `rowAmount` helper is not exercised on all subtitle branches. Fix the proportion of pending rows, since they sit at the top and are the ones a reviewer looks at. Generate records in C++ via a fixture entry point rather than through `fixtureAddBlocks`, which only produces one mined group per call. Note that today there is no entry point to load N arbitrary records; the benchmark will need one, and it must be fixture-gated like the others.
- **Five fresh-process repeats per page.** Good. Report median and min, not mean, and show all five. Warm-up: discard the first toggle in each process, since the first `amount::format` and first `Shape` tessellation pay one-time costs that are not the thing being measured. If you want cold-path cost, report it as a separate "first toggle" number.
- **Latency endpoint.** "Monotonic `toggleExact` entry to first post-change `QQuickWindow::frameSwapped`" is the right endpoint, with two caveats. First, connect to `frameSwapped` with `Qt::DirectConnection` and record the timestamp on the render thread; a queued connection adds a scheduling hop. Second, the first frame after `toggleExact` returns is not guaranteed to contain the new rows at N=1000: delegate creation can span frames if the scene graph syncs before QML finishes instantiating. Verify by also asserting, at the time of the swap, that `Wallet.activity.count` rows have delegates (`Repeater.count` equals model count) and that the last delegate's `amountText` matches the model. Otherwise the metric under-reports the baseline and makes the optimization look smaller than it is.
- **Synchronous refresh separately.** Yes. Measure `refreshModels()` wall time inside `toggleExact` with the same monotonic clock. Report it alongside, and also report the gap, since the gap is the render cost the `dataChanged` change targets.
- **CPU and RSS.** `getrusage(RUSAGE_SELF)` captures both threads, which is what you want. Sample before and after each toggle, not per process. Peak RSS (`ru_maxrss`) is high-water and cannot decrease, so it is only meaningful on the first toggle after the records load; after that it just reports the maximum. Add `PSS` from `/proc/self/smaps_rollup` if you want a per-toggle memory figure.
- **Counters.** Model reset and `dataChanged` counters should be attached via `QAbstractItemModel` signals from the benchmark, not by editing the model, so baseline and optimized use byte-identical instrumentation. Delegate creation and destruction need a counter on the `Repeater`'s `itemAdded` and `itemRemoved` signals; that is the honest measure of delegate churn and is observable from QML without touching `ActivityList.qml`. Also count `Accessible.name` re-evaluations if your harness can, since that is the a11y cost.
- **Identical instrumentation.** The benchmark must be a separate build target or a runtime flag that both binaries accept, and the flag must be off in the reproducible-build check in the README. If the instrumentation lives in the app binary it changes `sha256sum` of `meownero-wallet`, which TJS-2018 recorded as evidence. Keep the benchmark in `wallet-ui/tests` or a new `wallet-ui/bench` target and link `wallet_core`, loading the same QML module.
- **Safety bounds.** 60 s and 512 MiB sequential bounds are fine for this app; the 1000-row baseline on the reset path should be well under both. If the 60 s wall bound trips on the baseline, record it as a measured failure, not as "infinite".
- **Reduced motion.** `PageBase` and `AppDialog` animate. Run with the reduced-motion hint forced on so page entry animation does not land in the frame window. State this in the report.
- **Platform.** Say which QPA and GL backend ran (xcb vs offscreen, software vs GL). An `offscreen` platform still fires `frameSwapped`, but its render cost is not representative. Prefer xcb under Xephyr, which TJS-2018 already set up.
- **Correctness gate per run.** After each toggle, read back all rows' `amountText`, `amountAccessible`, `statusText`, and row order, and diff against a reference computed by calling `detail()` on the same ids. That makes "order, pending-first, amounts, status, accessible names preserved" a measured property of the optimized build rather than a claim.
