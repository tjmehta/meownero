## Consumption and crash/OOM custody

The operator reserves the exact grant/attempt/commit/input/artifact/bootstrap in a manager-owned slot and sends a fresh 32-byte activation secret only through a private inherited one-use channel. The slot contains its hash, not the secret. Sending that secret is not repeatable after an uncertain outcome. The manager cannot create, delete or rearm a slot. A new or restarted process with a RESERVED disk record has recovery-only authority; the record alone is never permission to consume or start again.

After the first full fresh admission, the manager overwrites the existing slot with QUARANTINED, fsyncs it and verifies its bytes before the outer may create a local receipt. Missing/corrupt slot, lost activation, partial write, fsync failure or admission expiry prevents local consumption and provisioning. An error burns the in-memory instance. A recovered manager never resumes setup even if a prewrite crash left RESERVED intact. Local O_EXCL/file/directory fsync remains useful but no longer carries the independent quarantine obligation alone.

The keeper must pass the original lock's same open file description to PID1 with FDSTORE and retain a live copy. The source supplies FD transfer plus a separate processing barrier. The helper must independently read back actual same-description custody before it acknowledges retain. A successful `sendmsg`, processing barrier, configured FD store or duplicate in one Python process does not prove custody survival. `FileDescriptorStoreMax=1`, preservation, retained namespace access and restart recovery need actual source/version/operator binding and later authorized host tests.

Use an empty aggregate parent capped at 2 CPU/4 GiB/no swap/256 PIDs. Work children receive at most 3840 MiB/224 PIDs and grouped OOM. Manager/helper/recovery/observer receive at most 256 MiB/32 PIDs in the recovery branch; their phases share this allocation. Killing the work branch must preserve keeper/recovery. The source does not attest that this split supplies sufficient headroom, PID1 overhead accounting, immunity from host OOM, or independent absolute deadlines. A common-parent OOM/kill must not be used as a recovery recipe. Systemd alone is not that proof.

At controller/launcher crash, timeout or work OOM, the surviving keeper enters recovery. At keeper death, PID1 must retain the FD and restart into recovery-only mode with the original absolute deadlines and namespace reference. The operator must establish an independently enforced end at origin+4500, including recovery/export, and a final observer after launcher/recovery exit. Recovery failure retains/quarantines custody and records failure; it never yields a success or makes the grant reusable. Power loss/reboot is failure and quarantine, not a same-open-description survival claim.

[Docker dedicated daemon options](https://docs.docker.com/reference/cli/dockerd/) support private paths and disabled bridge/firewall options. [util-linux loop lifecycle](https://man7.org/linux/man-pages/man8/losetup.8.html) documents explicit device setup, sizelimit, nooverlap's find/reuse behavior and delayed detach. These primary sources were retrieved for this source delta; actual host compatibility remains unverified.
