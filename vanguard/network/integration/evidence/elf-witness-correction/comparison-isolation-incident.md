# Baseline comparison isolation incident

An evidence-only helper imported the baseline controller separately from the current test module. Its first attempt refused before lock acquisition because the substituted runner-hash binding did not match. The next attempt fixed that binding but patched only the current module's lock constants, not the separately imported baseline module's `g.LOCK`/`LOCK_ID`. The baseline therefore briefly acquired the original nonblocking heavy lock. Its substituted first admission then asserted that the disposable test lock was held; that assertion failed. The controller finalized with REFUSED_BEFORE_ATTEMPT, without creating the output root, staging, issuing any Docker call or starting any native process, and closed the original lock descriptor in its finally block. The helper's postcondition assertion failed. This was an isolation error and an unauthorized lock touch; it is not native acceptance or a capacity probe.

The successful comparison explicitly patches BOTH baseline `g.LOCK` and `g.LOCK_ID` to the disposable case lock, then confirms actual baseline main refuses the real emitted build.json after one substituted build start and before any substituted runtime start. Current-candidate connected tests already patch their module's lock in setUp and were unaffected. No production code correction resulted from this comparison error. The original lock was neither unlinked nor replaced; no native grant was consumed. No further original-lock operation was performed.
